TENSORSTORE MODEL CHECKPOINTING: EXPERIMENTAL RESULTS AND ANALYSIS
====================================================================

This document presents the results from comprehensive experiments comparing different approaches for saving and loading large language models using TensorStore. The experiments evaluate PyTorch's native checkpointing against TensorStore implementations, examining the impact of various configuration parameters including compression, concurrency, and chunk sizes across multiple model architectures.


PLOT 2: PHASE COMPARISON - PYTORCH VS TENSORSTORE VS T5X
==========================================================

What was tested?
This experiment compares three different checkpointing approaches across four models (Qwen2.5-7B, OpenLLaMA-3B, Llama-3.2-3B, and Mistral-7B). The three approaches are: (1) PyTorch's native torch.save with no compression, (2) our TensorStore implementation with 64 MB chunks and no compression, and (3) T5X's TensorStore approach with 64 MB chunks and gzip compression.

What were the results?
PyTorch consistently demonstrates the fastest save and load times across all models, with save times ranging from 5-15 seconds and load times around 3-5 seconds. Our TensorStore implementation shows significantly slower performance, with save times of 140-300 seconds and load times of 17-30 seconds. The T5X approach falls between the two, with save times of 60-150 seconds and load times of 25-40 seconds. File sizes are comparable across all three methods, ranging from 2.6-6.7 GB depending on the model.

Why do we see these variations?
PyTorch's superior performance stems from its highly optimized native serialization that writes data sequentially with minimal overhead. TensorStore, while offering advantages in distributed systems and cloud storage, incurs significant overhead from its chunked storage format and metadata management. Each parameter must be written as a separate Zarr array with associated metadata, resulting in hundreds of individual file operations. The T5X approach improves upon basic TensorStore by using higher concurrency (128 operations) and gzip compression, which reduces I/O wait times despite the compression overhead. However, both TensorStore approaches remain slower than PyTorch for local disk operations because they are optimized for different use cases - distributed training and cloud storage rather than single-machine checkpointing.


PLOT 3: COMPRESSION COMPARISON - GZIP VS NO COMPRESSION
========================================================

What was tested?
This experiment evaluates the impact of gzip compression on TensorStore checkpointing performance using two models (OpenLLaMA-3B and Llama-3.2-3B). Both models were saved with identical configurations except for compression: one with no compression and one with gzip compression. The chunk size was fixed at 64 MB and concurrency at 128.

What were the results?
For both models, compression significantly increases save times. OpenLLaMA-3B shows save times increasing from approximately 140 seconds without compression to 180 seconds with gzip, while Llama-3.2-3B increases from 160 seconds to 200 seconds. Load times also increase with compression, rising from 18-20 seconds to 25-30 seconds. However, compression provides minimal file size reduction, with sizes decreasing by only 2-5% (from 2.60 GB to 2.55 GB for OpenLLaMA-3B).

Why do we see these variations?
The performance degradation with compression occurs because gzip must process every byte of data during both save and load operations, adding substantial CPU overhead. Modern neural network weights are already relatively incompressible because they consist of floating-point numbers with high entropy. Unlike text or structured data, these numerical values don't contain repetitive patterns that compression algorithms can exploit effectively. The minimal file size reduction (2-5%) confirms this - the compression overhead costs significant time but yields little benefit. For local storage where disk space is abundant, compression is counterproductive. However, compression might be worthwhile in bandwidth-constrained scenarios like cloud storage where network transfer costs dominate.


PLOT 4: CONCURRENCY COMPARISON - MISTRAL-7B AND QWEN2.5-7B
===========================================================

What was tested?
This experiment examines how different concurrency levels affect TensorStore performance for two 7B parameter models (Mistral-7B and Qwen2.5-7B). Concurrency levels tested were 1, 4, 16, 64, and 128 concurrent operations. All experiments used 64 MB chunks with no compression.

What were the results?
Both models show dramatic performance improvements as concurrency increases from 1 to 16, with diminishing returns beyond that point. For Mistral-7B, save times decrease from approximately 450 seconds at concurrency=1 to 280 seconds at concurrency=16, then plateau around 260 seconds for higher concurrency levels. Qwen2.5-7B follows a similar pattern, dropping from 420 seconds to 250 seconds as concurrency increases to 16. Load times show similar trends but with smaller absolute improvements. File sizes remain constant at approximately 6.7 GB regardless of concurrency level.

Why do we see these variations?
The performance improvements from increased concurrency occur because TensorStore can overlap I/O operations. At concurrency=1, each chunk must be written sequentially, forcing the system to wait for each disk operation to complete. Higher concurrency allows multiple chunks to be written simultaneously, hiding I/O latency and better utilizing available disk bandwidth. The plateau effect beyond concurrency=16 suggests that we've reached the practical limits of the storage system's parallel I/O capabilities. Modern SSDs can handle 16-32 concurrent operations efficiently, but beyond this point, the disk becomes the bottleneck rather than the concurrency level. The lack of improvement from 64 to 128 concurrent operations indicates that the storage system is already saturated at 64, and additional concurrency only adds scheduling overhead without improving throughput.


PLOT 5: CONCURRENCY COMPARISON - LLAMA-3.2-3B AND OPENLAMA-3B
==============================================================

What was tested?
This experiment mirrors Plot 4 but focuses on smaller 3B parameter models (Llama-3.2-3B and OpenLLaMA-3B). The same concurrency levels (1, 4, 16, 64, 128) were tested with identical configurations: 64 MB chunks and no compression.

What were the results?
The 3B models show similar concurrency scaling patterns to the 7B models but with faster absolute times due to their smaller size. OpenLLaMA-3B save times decrease from 280 seconds at concurrency=1 to 140 seconds at concurrency=16, while Llama-3.2-3B drops from 300 seconds to 160 seconds. Both models plateau around concurrency=16, with minimal improvements at higher levels. Load times follow the same pattern, decreasing from 30-35 seconds to 18-22 seconds as concurrency increases to 16. File sizes remain constant at approximately 2.6 GB.

Why do we see these variations?
The smaller models exhibit the same concurrency scaling behavior as larger models, confirming that the performance characteristics are driven by the storage system's parallel I/O capabilities rather than model size. The faster absolute times simply reflect that there's less data to write. The plateau at concurrency=16 appears to be a fundamental characteristic of the storage hardware being used, likely an SSD with optimal performance at 16-32 concurrent operations. Interestingly, the percentage improvement from concurrency scaling is similar across both 3B and 7B models (approximately 50% reduction in save time from concurrency=1 to concurrency=16), suggesting that the benefits of parallelization scale proportionally with model size.


PLOT 6: CHUNK SIZE COMPARISON - ALL FOUR MODELS
================================================

What was tested?
This comprehensive experiment evaluates how chunk size affects TensorStore performance across all four models (OpenLLaMA-3B, Qwen2.5-7B, Llama-3.2-3B, and Mistral-7B). Six different chunk sizes were tested: 1 MB, 4 MB, 16 MB, 64 MB, 128 MB, and 256 MB. All experiments used default TensorStore concurrency and no compression.

What were the results?
All models show a clear trend: very small chunk sizes (1-4 MB) result in significantly slower performance, while larger chunk sizes (64-256 MB) provide optimal and relatively stable performance. For the 7B models (Qwen2.5-7B and Mistral-7B), save times at 1 MB chunks are approximately 400-450 seconds, decreasing to 250-280 seconds at 64 MB chunks and remaining stable through 256 MB. The 3B models (OpenLLaMA-3B and Llama-3.2-3B) show similar patterns with proportionally faster times: 250-280 seconds at 1 MB decreasing to 140-160 seconds at 64 MB and above. Load times follow similar trends. File sizes remain constant across all chunk sizes, confirming that chunking is purely a storage organization strategy.

Why do we see these variations?
Small chunk sizes create excessive overhead because each chunk requires separate metadata, file operations, and I/O calls. With 1 MB chunks, a 7B model might be split into thousands of individual chunks, each requiring its own Zarr array metadata and file handle. This creates significant filesystem overhead and prevents efficient sequential I/O. Larger chunks (64-256 MB) reduce the number of separate operations and allow the storage system to perform more efficient sequential writes. The performance plateau at 64 MB suggests this is the sweet spot where chunks are large enough to minimize overhead but small enough to allow reasonable parallelization. Beyond 64 MB, further increases provide no benefit because the chunks are already large enough to amortize the fixed costs of metadata and file operations. The consistency of this pattern across all four models indicates that 64 MB is a robust default choice for TensorStore chunking regardless of model size.


PLOT 7: CHUNK SIZE COMPARISON - OPENLAMA-3B AND LLAMA-3.2-3B
=============================================================

What was tested?
This experiment provides a focused comparison of chunk size effects on two 3B parameter models (OpenLLaMA-3B and Llama-3.2-3B). The same six chunk sizes (1, 4, 16, 64, 128, 256 MB) were tested with identical configurations to Plot 6.

What were the results?
Both 3B models demonstrate nearly identical chunk size scaling behavior. Save times start at approximately 250-280 seconds for 1 MB chunks, decrease sharply to 160-180 seconds at 16 MB chunks, and plateau at 140-160 seconds for 64 MB and larger chunks. Load times show a similar pattern, starting at 30-35 seconds for small chunks and stabilizing at 18-22 seconds for 64 MB and above. The two models track each other closely across all chunk sizes, with differences of less than 10% at any given chunk size.

Why do we see these variations?
The close agreement between the two 3B models confirms that chunk size effects are primarily determined by model size rather than architecture-specific factors. Both models have similar parameter counts (approximately 3 billion) and therefore similar total checkpoint sizes (around 2.6 GB), leading to nearly identical chunking behavior. The sharp performance improvement from 1 MB to 16 MB chunks reflects the transition from excessive fragmentation to reasonable chunk counts. At 1 MB, these models are split into roughly 2,600 chunks, while at 64 MB they're divided into only about 40 chunks. This 65x reduction in chunk count dramatically reduces metadata overhead and filesystem operations. The plateau at 64 MB indicates that further chunk size increases don't help because we've already reached the point where chunking overhead is negligible compared to actual data transfer time.


KEY INSIGHTS AND RECOMMENDATIONS
=================================

Based on these comprehensive experiments, several clear patterns emerge:

For local disk checkpointing, PyTorch's native approach remains significantly faster than TensorStore, with 10-20x better save performance and 5-8x better load performance. TensorStore's advantages lie in distributed systems and cloud storage scenarios, not single-machine local disk operations.

Compression provides minimal benefits for neural network checkpoints. The 2-5% file size reduction doesn't justify the 20-40% performance penalty. Compression should only be used when network bandwidth or storage costs are critical constraints.

Concurrency significantly improves TensorStore performance, but with diminishing returns beyond 16 concurrent operations. For most systems, concurrency=16 provides the optimal balance between performance and resource usage. Higher values add complexity without meaningful benefits.

Chunk size has a dramatic impact on performance, with 64 MB emerging as the optimal choice across all tested models. Smaller chunks create excessive overhead, while larger chunks provide no additional benefits. This 64 MB sweet spot appears to be model-size independent and should be used as a default.

Model size affects absolute performance but not relative scaling characteristics. Larger models take proportionally longer to save and load, but they benefit from concurrency and chunk size optimizations in the same proportions as smaller models.

For production use, the recommended TensorStore configuration is: 64 MB chunks, no compression, and concurrency=16. This provides the best balance of performance, simplicity, and resource efficiency across different model sizes and hardware configurations.
